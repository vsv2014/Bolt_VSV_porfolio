Render 10,000 rows without rendering 10,000 elements

Windowing math, overscan and scroll batching in a dependency-free React table

By Santhosh Vishal · 2026-11-12 · 5 min read

If a table contains 10,000 records, mounting 10,000 row elements is usually unnecessary. The interactive portfolio table demonstrates fixed-height list virtualization: all 10,000 synthetic data rows are available in memory, but only a small slice is rendered into the DOM.

Why fixed-height windowing is tractable

The demo uses a 30-pixel row, a 260-pixel viewport and six overscan rows on each side. With known row height, the visible interval can be calculated from scrollTop without measuring each item. Clamp the viewport and scroll position to avoid negative ranges, and cap the resulting end index at total.

const start = Math.max(0,
  Math.floor(scrollTop / rowHeight) - overscan);
const end = Math.min(total,
  Math.ceil((scrollTop + viewportHeight) / rowHeight) + overscan);

This gives a predictable number of elements: usually roughly ceil(viewportHeight / rowHeight) + 2 × overscan, rather than 10,000. The underlying visibleRange() helper additionally clamps scroll positions near the end of the list.

The illusion of a full-height list

A tall inner spacer remains at total × rowHeight so the browser scrollbar knows the full scrollable distance. The rendered window is translated by start × rowHeight. As you scroll, the window changes, but the scroll bar behaves as though every row exists in the document.

<div style={{ height: TOTAL * ROW_H, position: 'relative' }}>
  <div style={{ transform: `translateY(${start * ROW_H}px)` }}>
    {rows.slice(start, end).map(renderRow)}
  </div>
</div>

Batch updates, measure the actual viewport

The scroll handler stores the latest scrollTop, then requests a single requestAnimationFrame callback to commit React state. ResizeObserver measures the real viewport height. That avoids assuming that the CSS layout will always match a hard-coded constant, a bug that previously left blank space below the visible table.

Accessibility has trade-offs

The scroll container is keyboard focusable and describes itself as a list of 10,000 tenants. Each rendered item exposes its position and total set size through aria-posinset and aria-setsize. For production data grids, assess roving focus, sortable headers, variable-height rows, screen-reader compatibility, virtualization during rapid keyboard navigation, and server-side loading. A fast list is not automatically an accessible grid.
